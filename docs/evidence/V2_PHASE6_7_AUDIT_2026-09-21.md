## Verdict

Phase 6/7's local reducer, WAL framing, durable-quorum patch, local snapshot
restore, and bounded arena have substantial test coverage and pass the host
sanitizer suite. The end-state checklist nevertheless overstates closure:

1. G-040 is false for a **replaced** voter and for any voter whose committed
   prefix is no longer locally present. There is no peer snapshot transfer.
2. G-043's objective is false as written even in steady state: log-body sync is
   off-thread, but every term, vote and commit-index update still performs a
   synchronous file `fsync`, rename and directory `fsync` on the consensus owner
   thread.
3. G-047 uses a reasonable atomic-replacement design instead of the plan's
   two-slot design, but its named test does not inject or recover across any of
   the replacement protocol's actual persistence cut points.
4. The committed-outbox authority bit is only a local `raft_is_leader` sample.
   It is not a read-index/lease proof and can therefore label an isolated old
   leader authoritative. The Phase 8 lease can only be as sound as the read used
   to renew it.
5. Current HEAD is not Phase 6/7 target-gated. The only NUC PASS is an ancestor;
   the later G-051 storage-isolation change is explicitly not gate-covered, the
   ARM64 gate has not run, and the pinned manifest omits shared storage code.
6. The block arena is bounded, but the replicated node as a whole is not:
   retained log payloads and two delivery queues grow until an external caller
   compacts or drains them, and no production V2 node currently supplies that
   lifecycle.

Consequently G-040, G-043 and G-047 should be reopened; G-036/G-038 should not
be used to imply linearizable authority reads; and all Phase 6/7 guarantees at
HEAD remain target-gate-unproven.

## Findings

### F1 — HIGH — a replacement voter cannot catch up after compaction (G-040)

The checklist promises that a “restarted or replaced voter” recovers all safety
and dedup state before normal participation
(`docs/V2_END_STATE_GUARANTEE_CHECKLIST.md:208-209`). The implementation only
loads a snapshot from the voter's own directory
(`src/v2_replication.cpp:81-102`). `PeerMessage` handles RequestVote and
AppendEntries only (`src/v2_replication.cpp:488-555`); no message carries a
snapshot. Once `compact()` polls the prefix and discards it from both WALs
(`src/v2_replication.cpp:417-460`), the leader has neither log entries nor a
snapshot transport with which to seed a fresh voter.

Independent ASan+UBSan probe, using three real `ReplicatedKernel` voters:

1. commit indices 1 through 8;
2. compact the leader through index 8;
3. destroy a follower, delete only that follower's directory, reconstruct it
   with the same configured membership;
4. route/tick/flush all voters for 5,000 rounds.

Observed:

```text
leader_before=8 compacted=8
replacement=1 current=0 commit=0 applied=0 leader_commit=8
```

The probe exited 1 because the replacement never reached the leader's applied
index. This is not merely the documented “follower that loses committed history
needs an operator” limitation: it directly contradicts the checked G-040
sentence. Existing `install` coverage restarts a voter with its own snapshot and
directory (`tests/v2_replication_tests.cpp:722-750`); membership coverage does
the same. Neither exercises replacement/catch-up from peers.

Required disposition: narrow G-040 to local-disk restart, or implement and test
peer snapshot transfer before calling replacement recovery closed.

### F2 — HIGH — hard-state persistence still blocks the owner loop (G-043)

`persist_vote` and `persist_term` call `MetadataStore::save` synchronously inside
Raft callbacks (`src/v2_replication.cpp:631-657`). `persist_commit_index` does
the same on proposal, tick and peer-receive paths
(`src/v2_replication.cpp:182-210,363-368,463-485,560-564`). `save` opens a temp
file, writes it, synchronously `fsync`s it, renames it, then synchronously
`fsync`s the directory (`src/storage.cpp:147-180`). Those callbacks execute on
the consensus owner thread.

Moving only WAL-body writes to `WalWriter` therefore does not satisfy the Phase
7 objective “Remove synchronous storage blocking from the owner loop”
(`docs/V2_TDD_IMPLEMENTATION_AND_VALIDATION_PLAN.md:571-576`) or the unchecked
G-043 wording. The checklist's stated exception mentions only truncation and
compaction, not ordinary election/commit hard-state writes
(`docs/V2_END_STATE_GUARANTEE_CHECKLIST.md:274-281`). The storage benchmark cited
for the win measures the log staging path; it does not prove end-to-end owner-loop
latency including metadata persistence.

This does not by itself show a Raft safety violation—synchronous hard-state
persistence is conservative—but it falsifies the latency/ownership guarantee and
can cause tick gaps/election churn under slow storage.

Required disposition: either redesign hard-state persistence under an explicit
durability fence, or narrow G-043 to “WAL entry bodies do not synchronously sync
in steady state” and measure full owner-loop behavior including term/vote/commit
updates.

### F3 — HIGH — G-047's atomic-replacement protocol lacks cut-point recovery evidence

The plan requires “hard-state two-slot recovery chooses newest valid sequence”
(`docs/V2_TDD_IMPLEMENTATION_AND_VALIDATION_PLAN.md:585-586`), and G-047 claims a
“tested atomic/two-slot recovery protocol”
(`docs/V2_END_STATE_GUARANTEE_CHECKLIST.md:247-248`). Actual `PersistentMetadata`
has no sequence or slot identity (`include/velocita/storage.hpp:12-16`), and
`MetadataStore` maintains one authoritative file via temp-file replacement
(`src/storage.cpp:147-180`). Recovery either accepts that one file or throws;
there is no older valid slot to choose.

The named test explicitly substitutes atomic rename for the specified mechanism
(`tests/v2_replication_tests.cpp:1564-1570`), then creates and truncates
`metadata.torn` (`:1586-1588`) and intentionally loads the intact
`v2-metadata.bin` (`:1590-1595`) to establish that an unrelated torn file is
ignored. It later truncates the authoritative file and proves that startup
refuses (`:1597-1608`). Thus it does not inject a cut at
temp-file write, temp-file fsync, rename, or directory fsync, and it proves no
recovery behavior at those protocol boundaries.

Atomic replacement can validly satisfy the safety property without literally
using two slots; the implementation-plan mechanism is not itself mandatory.
What is unproved is the actual implementation's durability protocol under cuts,
especially the rename/directory-sync boundary and the intended treatment of a
leftover temp file. G-047 currently has fail-closed corruption-detection evidence,
not the claimed hard-state cut/recovery evidence.

### F4 — MEDIUM — `authoritative` is not authority under partition

`CommittedOutboxView::authoritative` is assigned directly from
`raft_is_leader(server_)` (`src/v2_replication.cpp:404-414`). The implementation
performs no read-index round trip, quorum confirmation, or bounded leader lease.
ADR 0005 and the source comments acknowledge this is weaker and defer read-index
discipline (`docs/adr/0005-reducer-behind-consensus.md:48-56`,
`include/velocita/v2/replication.hpp:120-133`). The Phase 6 implementation plan,
however, includes “leader/read-index discipline for authority-sensitive reads”
(`docs/V2_TDD_IMPLEMENTATION_AND_VALIDATION_PLAN.md:551-558`).

The test proves only that the currently healthy leader returns true and healthy
followers return false (`tests/v2_replication_tests.cpp:655-684`). It never
partitions an old leader, elects a new leader in the majority, and reads the old
leader. A Raft node does not necessarily cease believing it is leader merely
because it has stopped hearing a quorum, so a local role bit is not a
linearizable authority proof.

This matters beyond naming: `renew_authority` accepts an `AuthorityReading` when
its boolean is true (`src/v2_gateway.cpp:41-57`), and its documented source is
the committed-outbox authority answer (`include/velocita/v2/gateway.hpp:75-104`).
An isolated old leader can therefore renew the gateway lease unless deployment
adds a stronger read that does not exist in `ReplicatedKernel`.

Required disposition: expose a read-index/quorum-confirmed read or explicitly
forbid the local role bit from renewing external-send authority.

### F6 — MEDIUM — “bounded memory” stops at the WAL arena

The arena is genuinely fixed at 64 blocks (`include/velocita/v2/wal_arena.hpp:70-80`),
but `ReplicatedKernel` also owns an unbounded `std::map` of every log payload and
unbounded outbound-message and committed-result deques
(`include/velocita/v2/replication.hpp:274-289`). Payloads leave the map only when
Raft polls, pops or clears entries (`src/v2_replication.cpp:704-747`), and prefix
polling is driven by an explicit `compact()` call. There is no non-test caller of
`compact()` anywhere in the tree. The two deques likewise depend entirely on an
external caller continuously draining them.

This is not a defect in `WalBlockArena`; its refusal behavior is well tested. It
is a lifecycle gap in the Phase 7 “durability, bounded memory, snapshot, and
compaction” objective. A long-running node with no compaction scheduler retains
canonical command payloads indefinitely even though WAL staging remains bounded;
a stalled transport/result consumer grows the queues independently of the arena.
The handoff separately confirms that no V2 node binary exists, so no production
owner currently enforces drain or compaction thresholds.

Required disposition before live NUC/Pi operation: set bounded high/low
watermarks and a deterministic snapshot/compaction schedule; bound or apply
backpressure to outbound/results queues; test consumer stall and sustained log
growth through the actual node loop.
